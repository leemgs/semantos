\section{\sysname Testbed Details}
\label{app:testbed}
\paragraph{Design hypotheses.}
\sysname is motivated by three hypotheses. First, a configuration's utility may depend on workload and hardware. Second, joint knob effects may be non-additive. Third, performance, failure probability and intervention cost may conflict. Each hypothesis requires measured interventions with explicit baselines.

For a loss $L$, define an interaction contrast from four independently measured configurations:
\[
 I_{ab}=L(a,b)-L(a,b_0)-L(a_0,b)+L(a_0,b_0).
\]
For lower-is-better loss, negative $I_{ab}$ indicates a beneficial non-additive interaction relative to the chosen baseline. A bootstrap interval must resample independent runs, not individual requests from a single run. The sign can change with workload, value range or kernel version, so an edge needs its scope, configuration values, measurement IDs and uncertainty interval. Such an edge describes an empirical interaction, not an unconditional causal coupling.

A \textsc{depends-on} edge requires a validated admissibility rule or measured range conditioning; it cannot be inferred solely from the sign of $I_{ab}$. The seed graph is empty until edges pass this test. The principal question is whether a reasoner can use independently acquired evidence more effectively than an optimizer with the same inputs, after charging the cost of acquiring that evidence.

\paragraph{Restricted rank gate.}
The gate of \S\ref{sec:testbed} sets $\tau$ as follows; $Y=1$ marks an unsafe outcome.
\begin{proposition}[Restricted rank gate]\label{prop:recal}
Fix a score function before calibration. Suppose $n$ unsafe calibration scores and the next unsafe test score are jointly exchangeable. Set $j=\lfloor\alpha(n+1)\rfloor$ for $0<\alpha<1$. If $j=0$, veto all; otherwise let $\tau$ be the $j$th smallest unsafe calibration score and accept only when $u<\tau$. Then the unsafe-class acceptance probability, marginal over calibration and test scores, is at most $j/(n+1)\le\alpha$.
\end{proposition}
\noindent\emph{Proof.} By exchangeability the test score's rank among the $n+1$ scores is uniform; it falls below the $j$th calibration score only in the first $j$ ranks, and ties only reduce this.\hfill$\square$

The bound controls misses among unsafe actions, $\Pr(A=1\mid Y=1)$, not the unsafe fraction among accepted actions; a cost-selected threshold is capped at the rank threshold, and no unsafe calibration example implies veto-all. The gate accepts any fixed score; \S\ref{subsec:gate} evaluates it with a measured risk score rather than $u$.

\paragraph{Disagreement score.}
For a knob--value pair proposed in $v$ of $k$ samples, the reasoner's score is $u=0.7(1-v/k)+0.3(1-w)$, clipped to $[0.02,1]$, where $w$ is the strongest retrieved synergy weight (zero when absent). It is neither predictive entropy nor a calibrated probability. Failed samples stay in the denominator, and repeated copies of a fallback are not counted as independent votes.

\paragraph{Bundle contract.}
A request contains a nonempty bundle identifier and a list of recommendations with \texttt{id}, \texttt{knob}, \texttt{proposed}, \texttt{uncertainty}, and optional rationale and provenance. Each request submits one bundle. Duplicate knobs, nonfinite scores, unsupported controls, and example-policy bound violations reject the entire request. Dirty-ratio changes must supply both values and satisfy the example policy that the background ratio is less than the foreground ratio. This is a declared policy, not proof that a configuration improves any workload. If any score satisfies $u\ge\tau$, all members are vetoed; otherwise all are staged together. A concurrent bundle receives a conflict response. Dry-run results return \texttt{applied=[]} and list simulated members separately.

\begin{algorithm}[t]
\caption{Implemented dry-run bundle path}
\label{alg:control-loop}
\begin{algorithmic}[1]
\REQUIRE Validated bundle $B$, fixed score function, calibration threshold $\tau$
\STATE Validate every member and joint constraints before changing state
\IF{another bundle is active}
  \STATE Return conflict
\ENDIF
\IF{$\max_{a\in B}u(a)\ge\tau$}
  \STATE Record veto for all members; return
\ENDIF
\STATE Stage the complete bundle in memory at 5\%
\FOR{requested stage in $\{25,50,100\}\%$}
  \STATE Advance the simulated bundle; record the transition
\ENDFOR
\STATE On cancellation, clear the complete simulated bundle
\STATE Never infer an unsafe/safe training label from simulated completion
\end{algorithmic}
\end{algorithm}

\paragraph{Deployment requirements.}
A real actuator must snapshot all old values, validate the full target configuration and available host interfaces, serialize updates, verify readback, and restore every old value on failure. Multiple sysctl writes are not a kernel transaction: partial exposure must be measured and cannot be described as atomic hardware state. Canary shares require separate hosts or an appropriate isolation mechanism; changing a host-global sysctl cannot isolate a fraction of requests on that host. Missing, stale or malformed end-to-end telemetry must stop promotion. These capabilities are requirements, not features demonstrated by the dry-run state machine.

\paragraph{One illustrative decision trace.}
Consider supplied context with example values 5 and 15 for the two dirty ratios, and retrieved evidence IDs $e_1,t_1$. Suppose all three model samples agree on this pair and $w=0$, giving $u=0.30$. If an independently obtained threshold is $\tau=0.25$, the whole bundle is vetoed; if $\tau=0.35$, it can enter the dry-run canary after joint validation. The audit record includes the values, scores, threshold and decision. These numbers illustrate the contract and are not a measured recommendation or calibrated operating point. The initial artifact threshold is zero until calibration data is explicitly supplied.

\paragraph{Actuator.}
A separate adapter snapshots a child thread's timer slack and CPU affinity~\cite{LinuxTimerSlack,LinuxAffinity}, validates the target, applies both settings, verifies readback and restores both originals in a \texttt{finally} path, including after partial application. Updates are sequential, not an atomic kernel transaction.

\paragraph{Expected cost of gated acceptance.}
Let $Y=1$ denote an independently defined unsafe outcome and $A=1$ acceptance. An outcome label is not defined by whether a rollback happened. For example, a benchmark can predeclare a request deadline, count observed failures or deadline exceedances, and define an action-level breach from these raw observations in a fixed window. Rejected actions have unknown counterfactual outcomes unless evaluated in an isolated experiment; they must not automatically be labeled safe or unsafe.

\begin{theorem}[Cost identity]\label{thm:pac-cost}
For costs $c_{\rm FN},c_{\rm FP},\lambda\ge0$, define
$C=c_{\rm FN}\mathbf{1}\{Y=1,A=1\}+c_{\rm FP}\mathbf{1}\{Y=0,A=0\}+\lambda D$,
where $D\ge0$ is measured exposure or SLO debt. Write $\pi=\Pr(Y=1)$,
$q=\Pr(A=1\mid Y=1)$ and $r=\Pr(A=0\mid Y=0)$. Then
\[
\mathbb{E}C=c_{\rm FN}\pi q+c_{\rm FP}(1-\pi)r+\lambda\mathbb{E}D.
\]
For a zero-probability class its associated product is zero.
\end{theorem}
\noindent\emph{Proof.} Expand each indicator expectation as its joint probability and use the definition of conditional probability. Linearity requires no independence.\hfill$\square$

This is an accounting identity, not a claim of novelty or a safety bound. A bound $q\le\alpha$ controls misses among unsafe actions. A different bound $\Pr(Y=1\mid A=1)\le\alpha$ instead gives
$\Pr(Y=1,A=1)\le\alpha\Pr(A=1)$, not $\pi\alpha$. Likewise $r$ is a veto rate among safe actions, not the proportion of vetoed actions that are safe. We report all denominators separately.

For bundle-level calibration, $u$ denotes the maximum member score and $Y$ the independently observed bundle outcome. Per-knob labels alone do not establish a bundle-level guarantee.

Selecting a smaller threshold by a cost rule cannot enlarge the acceptance event. Selecting a larger threshold can invalidate the bound; therefore the implementation uses the minimum of the rank threshold and optional cost-selected cap. No unsafe calibration examples implies veto-all. Calibration-window diagnostics are not test-set estimates.

\paragraph{Drift and selective observation.}
Sliding windows and a drift detector~\cite{Bifet2007ADWIN} do not guarantee exchangeability or a deterministic recovery time. Under an explicitly justified total-variation bound on the \emph{joint calibration--test law}, the probability of the same event changes by at most that bound; a marginal score-distance statement alone does not establish it. We neither estimate that distance nor claim recovery. Online labels selected by acceptance introduce additional selection bias. The runtime holds its threshold at zero on detected change until an explicit refresh; refresh remains an exploratory operation, not proof of safety.

\paragraph{Protocol requirements beyond this study.}
Workload, hardware and session groups are fixed before graph induction and assigned to disjoint train, retrieval, calibration and test roles; hashes of graphs, sources, prompts and calibrators are frozen before test results are opened, and a validator rejects overlap or unknown lineage. For each bundle we count proposed, rejected, vetoed, accepted, staged, completed and rolled-back outcomes, report gate TP/FP/FN/TN with both $\#$unsafe-accepted$/\#$unsafe and $/\#$accepted, and leave unknown labels unknown; rollback precision needs independently labeled executed actions. A lower threshold accepts a subset of fixed candidates, but the unsafe fraction among survivors need not be monotone. Absolute per-workload metrics precede ratios against a named baseline; a Pareto claim needs several measured operating points per method. Drift studies must keep the threshold trajectory and held-out outcomes at each decision, and faithfulness is tested by deleting cited and matched uncited context under fixed seeds.

The empirical selector minimizes mean training-run P95 over the four configurations. A saturated two-factor representation encodes the same four means as a baseline, two main effects and their interaction; minimizing it adds no information to table lookup. Both selectors have the same 40 training runs and zero online search trials. An unchanged-control selector and a seeded uniform-random selector provide references. Choices are frozen before calibration and test. We evaluate these fixed selectors by paired \emph{offline replay} on the same measured test grid, not by separate closed-loop executions. \subsection{Staged Actuation}
Across 80 fresh executions, 66 stop on a stage breach and 14 complete all stages; all 80 restore and read back both original values. At 5 and 8\,ms, observed deadline misses are respectively $186/816$ and $190/880$; summed exposure durations are 4.106 and 7.066\,s. Early stops reduce the number of observed events, so these fractions cannot be compared directly with fixed-duration, no-stop runs to claim an anomaly reduction. The stop criterion itself is not independent ground truth for rollback precision.

\subsection{Local Baseline Measurements}
We executed three bounded microbenchmarks on the available host: an Intel Core i5-3570 with four logical CPUs, approximately 31.2\,GiB RAM, and Linux 6.17.0-23-generic. These runs characterize the measurement pipeline: no kernel knob was modified and no LLM or controller was compared.

Each workload had 10 separate invocations of 100 measured operations, preceded by 10 warm-up operations. Workload--run order was shuffled with seed 4088. SQLite inserts a 4\,KiB value and commits each transaction in WAL mode with synchronous=FULL. The file test overwrites a 64\,KiB region and calls fsync. The compression test compresses a fixed seeded 64\,KiB payload at zlib level 6 and verifies decompression. Latency is wall-clock operation duration from a monotonic nanosecond clock; the compression measurement includes verification. The raw log retains every operation, run ID, deadline and error flag, with a SHA-256 hash and software/environment manifest.

\subsection{Temporal-Holdout Kernel Interventions}
We additionally executed real Linux timer-slack and CPU-affinity interventions in fresh owned child processes, without modifying host-wide sysctls. The two factors were timer slack (50\,$\mu$s or 1\,ms, set by PR\_SET\_TIMERSLACK) and affinity (all four available CPUs or CPU 0). Every child checked kernel readback before recording events. This isolated measurement driver is separate from the dry-run \sysname actuator.

For each periodic wake-up interval (2 or 5\,ms), five training blocks and ten subsequent test blocks evaluated all four configurations. Within each block, the eight interval/configuration cases were randomly ordered using seed 4088. Each fresh process performed ten warm-up and 80 measured wake-ups against absolute monotonic-clock targets. The plan was written before execution; the configuration minimizing mean training-run P95 lateness was frozen before test execution. This is temporal holdout within one host and workload family, not the independent workload/hardware split required for claims of generalization. The complete 120-process experiment retained 9,600 event timestamps, readbacks, frozen selections and hashes. No external competing load was introduced.

\section{Prompt and Output Schema}
\label{app:prompt}
Every model receives the following system prompt:
\begin{quote}\small
Select one allowed config to minimize periodic wake-up P95 latency. Return JSON with config (exact allowed name), cited\_ids (evidence IDs), and explanation. Evidence contains measured training summaries and retrieval runs, not held-out test outcomes. Do not invent evidence.
\end{quote}
The user message is a JSON object with the four allowed configuration names and the evidence list for the input variant. Items have the forms
\begin{quote}\small\raggedright
\texttt{\{"id": "training-table", "kind": "table", "values": \{"s50000\_aall": 132.9413, ...\}\}}\\
\texttt{\{"id": "interaction", "kind": "graph", "contrast\_us": -18.62, "edges": [], "scope": "same measured table; graph is a reparameterization, not extra evidence"\}}\\
\texttt{\{"id": "retrieval-3-0-s50000\_aall", "kind": "retrieval", "config": "s50000\_aall", "period\_ns": 3000000, "p95\_us": 126.36\}}
\end{quote}
The output schema requires \texttt{config} from the allowed list, \texttt{cited\_ids} with at most six entries restricted to the supplied IDs (none for the no-evidence variant), and an \texttt{explanation} of at most 400 characters. Local models enforce it as a llama.cpp JSON grammar with greedy decoding; hosted models receive it as a strict JSON schema through OpenRouter, restricted to providers that honor it. Every answer is re-validated, and an invented or deleted citation makes it invalid; the explanation length is not re-checked, and 14 of 20 DeepSeek-V3.2 answers exceed 400 characters. Claim and citation counts in \S\ref{sec:results} are recomputed from these records by \texttt{claim\_taxonomy.py} and \texttt{citation\_analysis.py}. A single script, \texttt{reproduce\_paper.py}, reruns every analysis on a copy of the raw logs and checks that each table and quoted number in the paper is reproduced exactly; the supplementary \texttt{ARTIFACTS.md} maps each result to its data and script and includes a data statement. The supplementary records contain each prompt, its SHA-256 hash, the raw response and, for hosted models, the routed provider.

\paragraph{Claim-label checks and intervals.}
The 97 claim labels were drafted with an AI assistant. A rule-based check (\texttt{claim\_label\_autocheck.py}) re-derives the expected label of 56 claims directly from the evidence (values attributed to the training table, lists of runs, superlatives, ranges, thresholds, units and no-evidence claims) and agrees with every drafted label; flipping each label between \emph{correct} and \emph{wrong} is detected in 76 of 97 cases. The remaining 41 claims require judgment. One author then reviewed every label against the evidence, reading these 41 claims in full, and changed none (agreement with the draft 100\%); because the reviewer checked an existing draft, this is a confirmation rather than an independent annotation. For agreement, two further annotators who are not authors each labeled all 97 claims blind and independently, from the claims, their source sentences and written guidelines, without the drafted labels, checks or each other's labels. The first agrees with the verified labels on 94.8\% of claims over the seven labels (Cohen's $\kappa=0.918$) and 95.9\% for misstated versus not ($\kappa=0.914$); all five disagreements are claims this annotator judged correct (three ``significantly lower'' statements, one partly wrong claim, one range of cited runs). The second agrees on 90.7\% ($\kappa=0.856$) and 90.7\% ($\kappa=0.808$); five of its nine disagreements read ``lowest across all retrieval runs (runs 0--5)'' as restricted to runs 0--5, and two arise because the blind sheet showed a sentence from another seed for the claim (since fixed in \texttt{claim\_review\_agreement.py}). Over the verified labels and both annotators, Fleiss' $\kappa$ is 0.847 (seven labels) and 0.814 (misstated versus not), and the majority label equals the verified label for all 97 claims. The reported counts use the verified labels; with the annotators' labels, 37 and 38 rather than 41 of 97 claims are misstated. With 95\% Wilson intervals, the misstated proportions are 57\% (39--73\%) for local models, 36\% (26--48\%) for hosted models and 42\% (33--52\%) overall; 97\% (94--98\%) of cited retrieval runs belong to the chosen configuration and 80\% (75--85\%) come from the first half of the evidence list. These intervals treat claims and citations as independent, which overstates their precision because hosted explanations repeat claims across seeds. Two dependence-aware checks give similar values: counting each distinct claim of a model once, 25 of 67 (37\%) are misstated, and a bootstrap that resamples whole models gives 42\% (34--52\%) overall.

\paragraph{Entailment-based attribution judges.}
To test whether citation-support judges catch these errors, \texttt{entailment\_judge.py} gives each of the 93 evidence-based claims to eight judges with pinned revisions: three NLI cross-encoders (DeBERTa-v3-large trained on five NLI sets, DeBERTa-v3-large trained on SNLI/MNLI, RoBERTa-large-MNLI; \emph{supported} = entailment), Flan-T5-large asked whether the claim is fully supported (\emph{supported} = yes), and four judges trained to fact-check claims against grounding documents, AlignScore-large~\cite{Zha2023AlignScore} and MiniCheck with RoBERTa-large, DeBERTa-v3-large and Flan-T5-large backbones~\cite{Tang2024MiniCheck} (\emph{supported} = score above 0.5). As in citation-support evaluation, the premise is the verbalized evidence the model cited; the hypothesis is either the explanation sentence that states the claim or the extracted claim. Table~\ref{tab:entail} compares the judges with the author-verified labels. No judge separates misstated from correct claims well (balanced accuracy 0.47--0.68), and at least one judge accepts 28 of the 41 misstated claims. Lenient judges accept up to half of the wrong values, ranges and units, the near-misses that quote correct numbers; strict judges reject nearly all overstatements but also most correct claims. The fact-checkers are the strictest: MiniCheck accepts at most 3 of 51 correct claims. Correct claims about uncited evidence cannot be entailed by the cited items alone, but giving the two long-context MiniCheck judges all 42 evidence items as premise (claim$^*$) still leaves them near chance (0.49 and 0.52), because claims such as ranges and orderings require aggregating many items. TRUE (T5-11B) did not fit the 15\,GB of memory of our CPU container and was not tested.

\section{Robustness to Prompt, Evidence Order, Citation Cap and Decoding}
\label{app:robust}
\texttt{prompt\_robustness.py} reruns the full-context prompt of the six hosted models, five seeds each, with the same frozen evidence, strict JSON schema and OpenRouter settings as the main audit, under five conditions: a paraphrased system prompt; retrieval runs in reverse order; retrieval runs in a seed-specific random order; no citation cap (any number of supplied IDs); and sampling at temperature 0.7. All 150 answers are valid after one retry of two answers that a provider truncated. Table~\ref{tab:robust} reports the results. Every answer in every condition chooses the selector's configuration, and every cited run belongs to the chosen configuration (in the original runs only Gemini-Pro cites others). Reversing the runs moves citations with list position for four models (Llama-70B, Qwen3-235B and both Gemini models), whereas Nemotron keeps citing blocks 0--4 and DeepSeek-V3.2 falls in between; without the cap, four models cite all ten runs of the chosen configuration. The explanations of these new answers have no verified claim labels, so we score them with two automatic proxies, applied identically to the original runs: a universal quantifier attached to a comparison (``consistently the lowest'', ``lower in all runs'') or ``significantly lower'', which the evidence does not support; and decimal numbers that match no evidence value or derived minimum, maximum, mean or difference. The quantifier overstatement recurs in every condition (9 to 21 of 30 explanations, 21 in the original runs), while unsupported numbers are rare (at most two per condition), consistent with the verified finding that misstated claims mostly quote correct numbers.


\section{Mitigation Baselines}
\label{app:mitigation}
\texttt{mitigation\_baseline.py} reruns the full-context prompt of the six hosted models, five seeds each, with the frozen evidence, schema, citation cap and OpenRouter settings of the main audit, under three mitigations: an instruction added to the system prompt to check every number, range, extreme and comparison against the evidence, to avoid quantifiers the evidence does not support and to cite evidence for other configurations as well (\emph{verify}); one deterministic summary item per configuration added to the evidence, with the minimum, maximum and mean of its retrieval runs and the number of blocks in which it is lowest, a tool-style aid that removes hand aggregation (\emph{stats}); and both. All 90 answers are valid after one retry of five. These explanations have no verified claim labels, so Table~\ref{tab:mitigation} scores them with automatic checks applied identically to the 30 original hosted answers: the quantifier-overstatement proxy of Appendix~\ref{app:robust}; an exact range check, which flags a stated range for a configuration that equals neither the minimum and maximum of its runs nor those of the runs the answer cites; and unsupported decimal numbers. On the original answers, the range check flags exactly the seven explanations that contain a verified wrong range and no other, and the proxy fires for exactly the five models with verified overstatements.

Every answer in every condition still chooses the selector's configuration. The verify instruction removes almost all flagged quantifiers (21 to 1 of 30 explanations) and most range errors (7 to 2), but only the two Gemini models begin citing competing runs. Summary statistics remove range errors and lead 19 of 30 answers to cite a competing configuration's summary, yet four answers (three from Qwen3-235B, one from DeepSeek-V3.2) still call the control ``consistently'' lowest or the others ``significantly'' higher, although the supplied summary says it is lowest in 8 of 10 blocks; the one flagged verify answer restricts ``every run'' to runs 0--5. With both, no explanation is flagged. The checks see only two error types: reading every explanation for universal comparisons found residual errors that they miss, among them a verify answer stating that only runs 0--5 contain all four configurations (all ten blocks do) and a stats answer stating that all other configurations are typically above 748\,$\mu$s (\texttt{s50000\_aone} averages 227\,$\mu$s); the two remaining range flags under verify are both genuine. These mitigations therefore reduce the checkable errors substantially but do not certify an explanation; verified labels for the 90 explanations (exported for review with the records) are needed to measure their full effect.

\section{Reasoning Models}
\label{app:reasoning}
In the main audit, the two Gemini models reasoned internally by default (about 490 and 1,100 hidden reasoning tokens per answer for Flash and Pro); the other hosted models produced none. \texttt{reasoning\_models.py} toggles reasoning within a model on the full-context prompt, five seeds each, and compares with the same model's original answers: reasoning enabled for DeepSeek-V3.2 and Nemotron-3-Ultra-550B, the thinking variant of Qwen3-235B-A22B (Thinking-2507), and minimal reasoning effort for Gemini~3.8 Flash, whose endpoint refuses to disable reasoning. A first attempt showed that some providers silently drop reasoning when a strict JSON schema is requested, so an answer counts only if the requested reasoning was spent; DeepSeek-V3.2 is pinned to a provider that applies both, while Nemotron and the Qwen3 thinking variant, whose endpoints do not combine them, receive the schema in the prompt and are validated with the same rules. All 20 answers are valid and every reasoning arm spent 585 to 5,306 reasoning tokens.

Table~\ref{tab:reasoning} reports the automatic checks of Appendix~\ref{app:mitigation}. Reasoning changes no decision and does not make any model cite a competing configuration. It does not remove the quantifier overstatement: DeepSeek-V3.2 and the Qwen3 thinking variant still call the control ``consistently'' lowest in four and five of five explanations. Nemotron with reasoning makes fewer flagged errors (two overstatements and one wrong range, down from five each), but its explanations are also about half as long (190 versus 400 characters), so fewer claims are made; Gemini~Flash with minimal reasoning flags one explanation instead of two. These checks see only two error types and the answers have no verified labels, so the comparison shows that internal reasoning is not sufficient to remove the errors, not how many remain.

\section{Precision of the Local Models}
\label{app:precision}
The local models of the main audit ran as 4-bit GGUF files. \texttt{precision\_check.py} compares them with higher-precision reruns through the same \texttt{model\_audit.py} pipeline, with all input variants, cited and matched uncited deletion, five seeds, temperature~0 and the same 384-token limit: Llama-3.1-8B and Phi-4 with bf16 weights through OpenRouter, pinned to providers that declare bf16 (CoreWeave and DeepInfra), and Qwen2.5-7B as the official 8-bit (Q8\_0) GGUF in llama.cpp, the highest precision that fits our 15\,GB CPU machine. Qwen2.5-14B has no full-precision endpoint and was not rerun. The bf16 runs use a different serving stack and strict JSON schemas rather than a llama.cpp grammar, so any difference may come from precision or from serving.

Table~\ref{tab:precision} summarizes the comparison. In every evidence and no-evidence variant, each model makes the same choice as at 4 bits on every valid seed, including Llama-3.1-8B's wrong choice of \texttt{s50000\_aone} and the no-evidence choices; one bf16 Phi-4 answer without evidence is invalid. Explanation errors recur: Qwen2.5-7B again attributes the retrieval value 126.36 to the training table and again reads meanings into the configuration names without evidence; Phi-4 repeats its ``significantly lower'' claims almost verbatim; and Llama-3.1-8B, whose 4-bit explanations misstated values, now calls a list of single runs an average and claims the lowest average ``across all retrieval runs''. The one difference concerns reliance. With bf16 weights, Phi-4 cites the same six runs, but deleting them no longer changes its choice in any seed, whereas the 4-bit model switched in all five. Llama-3.1-8B changes its choice under both deletions at either precision (to a different wrong setting under cited deletion). The paper's only case of citation-specific reliance therefore does not survive a change of precision and serving stack.

\section{Redesigned Reliance Test}
\label{app:reliance}
The main audit's matched deletion has two weaknesses: the training table is a single item, so models that cite it have no same-kind control, and the uncited controls are runs of other configurations, so the two deletions differ in what the removed evidence says. \texttt{reliance\_redesign.py} reruns the test on the same frozen evidence, five seeds per model, for the six hosted models and for Llama-3.1-8B and Phi-4 with bf16 weights (Appendix~\ref{app:precision}). The training table is split into four per-configuration items, and two deletion tests follow each full-context answer: (A) the main audit's kind-matched test, now estimable when a table item is cited; and (B) a configuration-matched test that deletes $k$ cited retrieval runs of the chosen configuration versus $k$ uncited runs of the same configuration, with $k$ the smaller count (4--5 here). Controls are drawn with a seed-specific RNG.

Splitting the table leaves every hosted model's choice unchanged but turns bf16 Llama-3.1-8B from \texttt{s50000\_aone} to the control in all five seeds, so its earlier wrong choice depends on how the table is presented. Table~\ref{tab:reliance} gives the outcomes. Test A is estimable for 32 seeds and test B for 35; Gemini Flash cites all four table items, which leaves no table control. Under test B no hosted model and not Phi-4 ever changes its choice, while bf16 Llama-3.1-8B switches to \texttt{s50000\_aone} in all five seeds when its cited runs (blocks 0--4 of the control) are deleted and keeps the control when five uncited control runs are deleted. Test A agrees for Llama-3.1-8B and adds one DeepSeek-V3.2 seed, but its cited deletion removes the chosen configuration's own table entry while the control removes another configuration's, so test A still confounds citation with content. Even test B leaves different blocks in the prompt (in blocks 5--9 the competitor wins twice), so a change under cited deletion shows sensitivity to the cited items, not that the model's computation used them. Together with Appendix~\ref{app:precision}, these results show that citation-specific reliance appears in at most one model per design and that which model shows it depends on weight precision and on how the evidence is formatted.

\section{Further Evidence Instances}
\label{app:instances}
The main audit gives every model one evidence list. To test whether the findings depend on it, \texttt{evidence\_instances.py} reruns the six hosted models (same system prompt, schema, six-citation cap, temperature~0, five seeds; 90 calls, 0.45~USD) on three further instances built only from training-side data, so no test outcome enters a prompt. \emph{I1} keeps the training table but replaces the retrieval runs with the 40 calibration runs at 4\,ms; there the table's choice is lowest in only 5 of 10 blocks, and \texttt{s50000\_aone} has the lowest single run but a run mean twice as high (263.0 versus 121.5\,$\mu$s). \emph{I2} is the main evidence with the four labels permuted, so the best configuration is named \texttt{s1000000\_aone}, the name that suggests the worst setting. \emph{I3} comes from the separate measurement session of Appendix~\ref{app:measurements}: a table from its five training blocks at 2\,ms and its 20 training runs at 5\,ms as retrieval items. The graph item is omitted. Answers are scored with the automatic checks of Appendix~\ref{app:mitigation} against each instance's own evidence. The quantifier proxy counts ``consistently''/``all'' lowest only if the chosen configuration is not lowest in every block and ignores ``lowest average''; ``significantly'' always counts, since the evidence contains no test. These explanations have no verified claim labels.

Table~\ref{tab:instances} gives the results. Every answer is schema-valid. With I2 all 30 answers choose the relabeled best configuration, so the choice follows the evidence, not the names. With I3 all 30 choose the table's choice. With I1, where the runs disagree with the table more often, Llama-3.3-70B chooses \texttt{s50000\_aone} in all five seeds and Qwen3 in one. Llama-3.3-70B's explanations claim that configuration has the lowest average, and Qwen3's that it is consistently lowest; neither the table nor the runs support either claim. So the evidence suffices for a table-lookup choice only when the runs do not compete with the table. One-sided citation persists in every instance: only Gemini Flash cites competing runs (6 of 155 in I1). Front-loading cannot be measured in I3, where five runs per configuration fit under the cap. The quantifier proxy fires in 13--18 of 30 explanations per new instance, against 21 in the main audit. In I2 ``consistently the lowest'' recurs for the relabeled configuration, while the range errors of the main audit disappear: Nemotron now gives the competing range correctly.

The range check flags six I1 and four I3 explanations. On reading, eight contain a wrong range: \texttt{s50000\_aone} given as 76.186--148.876 or 76.186--697.378 (its maximum is 705.847), the chosen configuration given as 85.9--129.5 (it reaches 312.316), and two run values given as the range of \texttt{s50000\_aone} in I3. The other two are acceptable approximations (``$\sim$900--1500'' and ``$\sim$85--102 across most runs''). The proxy also misses phrasings such as ``across all five retrieval runs''. In I3, Llama-3.3-70B averages the five chosen-configuration runs and reports 93.3188, 93.3392 or 93.39\,$\mu$s; the mean is 93.339, so the computed values in its explanations are close but wrong. The reading was done with an AI assistant and has not been independently verified; \texttt{explanations-for-review.csv} lists every explanation with its flags. All three instances come from the same host and workload family as the main audit, so they test robustness to the evidence values, their order and the labels, not to other domains.

\section{A Second Domain: Database Settings}
\label{app:sqlite}
Much LLM configuration work tunes databases~\cite{Trummer2022DBBERT,Lao2024GPTuner,Giannakouris2025LambdaTune}. \texttt{domain\_sqlite.py} therefore repeats the audit on a database task measured for this purpose. Four configurations cross SQLite's \texttt{synchronous} setting (NORMAL or OFF) with its journal mode (DELETE or WAL). The objective is the P95 commit latency of write transactions of ten 100-byte rows. Each run is a fresh process with a fresh database file and records 10 warm-up and 200 measured transactions; the readback confirms every setting. Training, retrieval and held-out test roles of ten blocks each are separated in time, with configurations randomized within blocks under a plan written before measurement (SQLite~3.45.1, the four-core container of Appendix~\ref{app:prompt}). The evidence has the same format as the kernel task: a training table and 40 retrieval runs in block order. The task differs in three ways: the labels are descriptive, so priors about SQLite apply; the evidence sources disagree; and the measurements were committed before any model call. The table favors \texttt{sync\_off\_wal} (71.7 versus 99.5\,$\mu$s for \texttt{sync\_normal\_wal}). In the retrieval runs, \texttt{sync\_normal\_wal} has the lower mean (61.7 versus 64.3\,$\mu$s) and wins 8 of 10 blocks. On the test blocks, \texttt{sync\_off\_wal} has the lower mean P95 (47.4 versus 56.0\,$\mu$s) and wins 7 of 10. Its paired advantage is $20.6\pm26.7\%$, so the two WAL settings are not reliably separated.

The six hosted models answered the main audit's prompt and schema, with only the objective changed, under the full evidence and with no evidence (five seeds each; 0.28~USD including retries). Three full-evidence answers stayed invalid after one retry (two truncated, one over the citation cap). Table~\ref{tab:sqlite} gives the choices. Without evidence, 25 of 30 answers choose \texttt{sync\_off\_wal}, the test-best setting, which reflects common knowledge about SQLite. With evidence, 21 of 27 choose \texttt{sync\_normal\_wal} and so follow the retrieval runs rather than the table. Only Gemini~3.1 Pro (five seeds) and one Gemini Flash seed keep the table's choice. The evidence thus changes the choice away from both the prior and the table, toward a setting that is not better on the test blocks. Citations are again selective. The 21 answers choosing \texttt{sync\_normal\_wal} cite no run of another configuration, and Gemini~3.1 Pro cites competing runs only from the two blocks in which its choice wins.

We read all 27 explanations against the evidence with an AI assistant; the reading has not been independently verified (\texttt{explanations-read.csv}). Thirteen contain at least one misstatement, all among the 21 answers choosing \texttt{sync\_normal\_wal}, and none were found in the six answers that keep the table's choice. The dominant error is new. Nine explanations misreport the training table so that it agrees with the choice: three Nemotron answers call \texttt{sync\_normal\_wal} lowest ``across both training and retrieval evidence'', two Nemotron answers call 99.496\,$\mu$s ``significantly lower'' than 71.652\,$\mu$s, and four Qwen3 or DeepSeek-V3.2 answers call it the table's lowest or better than \texttt{sync\_off\_wal}. Other errors repeat the kernel task's patterns. Five explanations claim the choice is ``consistently'' lowest (it wins 8 of 10 blocks). Four give a wrong range for \texttt{sync\_normal\_wal}, each omitting its 114.05\,$\mu$s run in block~3. One states a wrong median and one uses milliseconds. The automatic checks see only part of this: the quantifier proxy flags 9 explanations and the range check 4. The range check partly flags ranges that are correct for the stated blocks and misses one wrong range, and neither check detects the misreported table. In this domain, then, the decision departs from the equally informed selector, and the rationales misreport the evidence that contradicts the decision.
