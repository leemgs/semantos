\section{Evaluation Protocol}
\label{sec:evaluation}
This revision pre-registers the evaluation required to substantiate SemantOS;
it does not present synthetic output as measured hardware evidence.

\subsection{Provenance and splits}
Each completed hardware run produces an immutable raw log and one run-level CSV
record containing a unique run identifier, UTC timestamp, workload family,
server identifier, kernel release, code commit, method, repetition, split,
latency quantiles, throughput, anomaly numerator and denominator, unsafe
proposals, vetoes, rollbacks, and the raw-log SHA-256. The released aggregator
accepts only these records, derives anomaly rate from counts, and stores the
input digest. The lineage is raw log $\rightarrow$ run record $\rightarrow$
aggregate $\rightarrow$ paper table; no inverse generation is permitted.

We partition by workload family into train, validation, calibration, and test.
A leave-one-workload-family-out evaluation rebuilds the dependency graph,
retrieval index, model adaptation, and calibration threshold without any trace
or edge from the held-out family. Test labels remain sealed until every
configuration and threshold is frozen.

\subsection{Matched baselines and outcomes}
All methods receive identical telemetry, admissible actions, graph access where
indicated, trial budget, wall-clock budget, and safety runtime. We compare
rules+graph, BO+graph, RL+graph, LLM-only, graph+LLM, and the complete SemantOS
system. This factorial design isolates whether the LLM improves recommendation
quality beyond lookup or a traditional optimizer using the same input.

Primary outcomes are P50, P95, and P99 latency, throughput, and anomaly rate.
Secondary outcomes are unsafe proposals, veto rate, rollback rate,
time-to-convergence, tuning trials, operator time, and explanation fidelity.
An anomaly window is defined in Section~\ref{subsec:risk-controls}; every rate
is published with its numerator and denominator. At least 20 independent runs
per workload--server--method cell are planned, with confidence intervals and
all exclusions declared before unblinding.

\subsection{Multi-objective reporting}
A single point per method is a performance--safety comparison, not a Pareto
frontier. A frontier will be reported only if every method is evaluated at
multiple pre-registered operating points (e.g., safety thresholds or objective
weights); the nondominated envelope and every underlying point will be released.

\subsection{Scope of claims}
Smoke-test generators in the artifact are synthetic and are not evaluation
evidence. Benchmark workloads executed on recorded hardware are described as
benchmarks, not production or ``real-world'' deployments. Any future numerical
claim must be regenerated from released run-level data by the provenance
pipeline. Human-subject findings likewise remain out of scope until the
protocol, anonymized task-level records, exclusions, and analysis are released.
